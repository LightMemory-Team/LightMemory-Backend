# 遊戲計分與 z-score 算法總覽

> 整理日期：2026-10-11，2026-10-15、2026-10-26、2026-10-27 更新
> 資料來源：`feat/dashboard_and_weekly_report` 分支（已包含 `fridge_check` 合併，PR #66）
>
> 10/27 更新重點（依〈認知維度計分規格：標準化與冷啟動〉）：
> - **五款遊戲的第一場是「熟悉場」**：不算分（`z_score`、1～100 分數都是 `null`）、也不進任何歷史，排除第一次玩還不熟的練習效應；沿用 `GameSession.is_pretest` 欄位，煮菜過程原本的前測就是熟悉場
> - **基準改用收縮估計**：不再「自己滿 3 場才從全體硬切換到自己」。資料少時偏向其他使用者「個人內」的變異，自己的場次越多越偏向自己（第 8 節）
> - **二階段標準化**：指標加權合成後，再除以合成分數本身的標準差，六個維度的波動幅度一致，不再因為指標數量不同，讓指標多的維度（整理菜籃、日記）分數擠在 50 分附近
> - **各指標改為等權重**：冰箱檢查、市場買菜改成「正確率」「速度分」兩個指標各自轉 z（原本先加權成 `raw_score` 再轉 z）；聲影日記的 5 個小分數也改為等權重，不再跟 `communication_score` 的權重綁定
> - **儀表板、週報各維度分開解鎖**：某維度累計 3 筆有 z 就亮起，不再等 6 個都滿；週報只列已解鎖的維度（第 11 節）
> - 新增 `python manage.py recompute_scores`：把舊場次依新算法重算（第 8 節）
> - 結算結果的欄位名稱都沒變，分數的數值會變；新增 `is_pretest` 回應欄位給前端顯示「熟悉場」提示
>
> 10/26 更新重點（團隊討論決定）：
> - **所有 z 都跟自己的歷史比**：整理菜籃、冰箱檢查、市場買菜、聲影日記不再使用寫死的常模；冷啟動規則同菜市場找路（自己不滿 3 場借全體，全體也不夠為 `null`；10/27 起改為收縮基準，見上）
> - **所有 z → 分數統一為 50 + 25z（1～100）**：整理菜籃 `cognitive_flexibility_score`、冰箱檢查與市場買菜 `standard_score` 從 50 + 20z（10～90）改過來
> - 共用工具集中到 `games/zscore.py`（`metric_z_scores`、`z_score_to_display_score`），API 欄位名稱不變
> - 等測試資料累積夠了，再依真實資料決定常模
>
> 10/15 更新重點：
> - 菜市場找路、煮菜過程的 z 限制在 ±2，結算時存入 `z_score`
> - 菜市場找路、煮菜過程的 `total_score` 統一換算成 1～100
> - 整理菜籃結算時多存整體加權 `z_score`
> - 冰箱檢查、市場買菜依合併後的程式碼更新（z 改用 `raw_score` 計算）
> - 新增第 11 節：儀表板與週報表怎麼使用這些分數
>
> 用語原則：本 App 定位為「輔助維持認知活躍度」，分數僅反映遊戲表現，不作任何診斷用途。

## 1. 名詞說明

| 名詞 | 意思 | 例子 |
|---|---|---|
| **標準差** | 一組數字平常會上下晃動多少 | 正確率 0.6、0.8、1.0 → 平均 0.8，標準差 0.2 |
| **z-score** | 這次的表現離基準有「幾個標準差」遠 | z = 0 跟基準一樣；z = +1 比基準好 1 個標準差 |
| **比較基準** | 拿來比的「平均、標準差」。資料少時偏向其他使用者、越多越偏向自己（收縮基準，第 8 節） | 自己 0 場時完全用其他使用者的；自己有 n 場，自己的占比是 n ÷ (n + 3) |
| **熟悉場** | 每位使用者每款遊戲的第一場。第一次玩還不熟，分數會偏低，所以不算分、也不進歷史 | 第一場結束時 `z_score`、`standard_score` 都是 `null` |
| **二階段標準化** | 多個指標加權合成後，再除以合成分數本身的標準差，讓每個維度的波動幅度一樣 | 5 個指標的日記和 2 個指標的遊戲，分數擺動範圍一致 |
| **50 + 25z** | 把 z 換成長者、家屬看得懂的 1～100 分 | z = +1 → 75 分；z = −1 → 25 分 |

```
z = (這次的值 − 基準平均) ÷ 基準標準差
越低越好的指標（例如反應時間）要乘 −1，讓所有 z 都是「越高越好」
```

`50 + 25z` 搭配「z 限制在 ±2」使用時，分數落在 **1～100**（z = −2 算出 0，最低給 1 分）：

| z | −2 | −1 | 0 | +1 | +2 |
|---|---|---|---|---|---|
| 50 + 25z（最低 1） | 1 | 25 | 50 | 75 | 100 |

- **所有 z 換算的分數都用這個**（10/26 統一）：煮菜過程 `total_score`、整理菜籃 `cognitive_flexibility_score`、冰箱檢查與市場買菜 `standard_score`、週報表的能力分數。z 是 `null` 時分數也是 `null`
- 程式：`games/zscore.py` 的 `z_score_to_display_score`
- 10/26 以前整理菜籃、冰箱檢查、市場買菜用 50 + 20z（10～90），舊場次存的分數不會重算

> 程式用的是**樣本標準差**（除以 n−1，Python 的 `statistics.stdev`）。

## 3. 菜市場找路 market_route

雷達圖維度：**注意力**

### 3-1. 原始總分 `total_score`

程式：`games/market_route/market_score.py`

```
單次作答得分 = round(基礎分 × 難度係數) + 速度加成
單場總分     = 所有作答得分加總（答錯、超時為 0 分，不倒扣）
```

| 第幾次答對 | 基礎分 | | 階段 | 難度係數 |
|---|---|---|---|---|
| 第 1 次 | 10 | | basic | × 1.0 |
| 第 2 次 | 6 | | intermediate | × 1.3 |
| 第 3 次 | 3 | | advanced | × 1.6 |

- **速度加成**：答對且反應時間 ≤ 曝光時間 × 50% → **+2 分**
- **理論最高 333 分**：每場固定從 basic 開始，最快連續 3 題快速答對就升階
  - basic 3 題 × 12 + intermediate 3 題 × 15 + advanced 14 題 × 18 = 36 + 45 + 252 = 333

**結束畫面的 `total_score` 換算成 1～100**（`normalize_total_score`）：

```
total_score = round(原始總分 ÷ 333 × 100)，限制在 1～100（全錯也給 1 分）
```

| 原始總分 | 0 | 12 | 166 | 333 |
|---|---|---|---|---|
| `total_score` | 1 | 4 | 50 | 100 |

> 每題的 `score_earned`（作答當下的即時回饋）仍是原始分數，沒有換算。

### 3-2. z-score（注意力分數）

程式：`games/market_route/market_zscore.py` 的 `calculate_attention_z_score(session_id)`

> **不用 `total_score` 算 z**：總分乘了難度係數，升到高階的場次天生分數就高，分不出是「真的進步」還是「升階比較快」。

**第一步：每個階段各算 3 個指標**（只看每題的第 1 次作答）

| 指標 | 定義 | 方向 |
|---|---|---|
| 正確率 | 第 1 次就答對的題數 ÷ 該階段題數 | 越高越好 |
| 平均反應時間 | 第 1 次作答、非超時的反應時間平均 | 越低越好 |
| 收斂曝光時間 | 該階段最後一題的曝光時間 | 越低越好 |

**第二步：每個指標跟「同一階段」的基準比**

基準用收縮估計（第 8 節）：自己「同一階段」的歷史場次少時偏向其他使用者的個人內變異，自己越多越偏向自己；沒有其他使用者資料時，基準就是自己的平均與標準差。

```
z_正確率   =      (本場 − 基準平均) ÷ 基準標準差
z_反應時間 = −1 × (本場 − 基準平均) ÷ 基準標準差
z_曝光時間 = −1 × (本場 − 基準平均) ÷ 基準標準差
每個 z 都限制在 [−2, +2]
```

**第三步：階段內等權重合成**

```
階段分數 = (z_正確率 + z_反應時間 + z_曝光時間) ÷ 3
```

**第四步：依這場最高到達的階段，跨階段加權**

| 這場最高到達 | basic | intermediate | advanced |
|---|---|---|---|
| basic | 1.0 | – | – |
| intermediate | 0.3 | 0.7 | – |
| advanced | 0.2 | 0.3 | 0.5 |

```
合成分數 = Σ（階段權重 × 階段分數），只計入有資料的階段
```

**第五步：二階段標準化**

```
注意力 z = 合成分數 ÷ 合成分數的標準差，再限制在 [−2, +2]
```

合成分數的標準差用收縮估計：拿自己過去每一場（用這一場同一組基準算出的）合成分數當樣本，樣本少時偏向「指標互不相關」的理論值 √(Σ有效權重²)（3 個指標等權重 = √(1/3)）。

**範例**：自己有 3 場歷史、這場只玩到 basic（沒有其他使用者資料，基準就是自己的）

```
歷史正確率   0 / 0.5 / 1        → 平均 0.5、標準差 0.5
歷史反應時間 700 / 800 / 900    → 平均 800、標準差 100（越低越好）
歷史收斂曝光 1900 / 1800 / 1700 → 平均 1800、標準差 100（越低越好）
三場的合成分數 −1/3、0、+1/3 → 變異數和 2/9
理論變異數 = 3 × (1/3)² = 1/3 → 收縮後 (2/9 + 3 × 1/3) ÷ (2 + 3) = 11/45

這場 正確率 0.5（z 0）、反應時間 800（z 0）、收斂曝光 1700（z +1）
合成分數 = (0 + 0 + 1) ÷ 3 = 1/3
注意力 z = (1/3) ÷ √(11/45) ≈ 0.674
```

- 最終 z 限制在 ±2
- **第一場是熟悉場**：不算分（`z_score` 為 `null`）、也不進之後場次的歷史；`total_score` 是原始分換算，第一場照常有
- **結算（`finish/`）時算好**，四捨五入到小數 3 位，存入 `result.z_score` 並回傳；資料不足時是 `null`
- 結算時這場還沒有 `finished_at`，會跟「所有已結束場次」比，結果跟之後再算一樣

冷啟動、資料不足的處理見第 8 節。

## 4. 煮菜過程 memory_recall

雷達圖維度：**工作記憶**

### 4-1. 每輪得分 `score_earned` 與結束畫面 `total_score`

程式：`games/memory_recall/score.py`

**每輪得分**（作答當下的即時回饋，沒有改）：

```
單輪得分 = round(10 × 難度係數)，答錯 0 分
```

| 階段 | 答對得分 |
|---|---|
| basic | 10 |
| intermediate | 13 |
| advanced | 16 |

- **不加速度分**：計時制下，反應快的人自然能答更多輪

**結束畫面的 `total_score`**（`games/zscore.py` 的 `z_score_to_display_score`）：

原始分數加總**沒有固定上限**（一場最長 90 秒，答得越快輪數越多），沒辦法等比例換成 1～100，所以改用本場的工作記憶 z（見 4-2）換算：

```
total_score = round(50 + 25 × 工作記憶 z)，限制在 1～100
```

| 工作記憶 z | −2 | −1 | 0 | +1 | +2 | `null` |
|---|---|---|---|---|---|---|
| `total_score` | 1 | 25 | 50 | 75 | 100 | `null` |

- **前測**、**歷史不足算不出 z**：`total_score` 為 `null`，前端顯示提示文字
- 舊的「單場總分 = 所有答對輪得分加總」不再回傳；`calculate_total_score` 函式保留但結算沒有使用
- 舊的 X-score（`normalize_to_100`）已刪除

### 4-2. z-score（工作記憶分數）

程式：`games/memory_recall/memory_zscore.py` 的 `calculate_working_memory_z_score(session_id)`

比照菜市場找路的五步驟，差別如下：

| | 菜市場找路 | 煮菜過程 |
|---|---|---|
| 每階段指標 | 正確率、反應時間、收斂曝光時間 | **正確率、反應時間** |
| 階段內權重 | 等權重（各 1/3） | **等權重（各 1/2）** |
| 只看第 1 次作答 | 是（可以重看） | 不需要（每輪只答一次） |
| 熟悉場 | 第一場 | 第一場，就是原本的**前測**；**本身回傳 `None`**，也**不進之後場次的歷史** |

```
階段分數   = (z_正確率 + z_反應時間) ÷ 2
工作記憶 z = 合成分數（跨階段權重同菜市場找路）÷ 合成分數的標準差，再限制在 [−2, +2]
```

**範例**：自己有 3 場 basic 歷史（沒有其他使用者資料，基準就是自己的）

```
歷史正確率   0 / 0.5 / 1          → 平均 0.5、標準差 0.5
歷史反應時間 1000 / 1100 / 900    → 平均 1000、標準差 100（越低越好）
三場兩個指標的 z 是 (−1, 0)、(0, −1)、(+1, +1) → 合成 −0.5、−0.5、+1 → 變異數和 1.5
理論變異數（2 個指標等權重）0.5 → 收縮後 (1.5 + 3 × 0.5) ÷ (2 + 3) = 0.6

這場 正確率 0.5（z 0）、平均反應時間 950（z +0.5）
合成分數 = (0 + 0.5) ÷ 2 = 0.25
工作記憶 z = 0.25 ÷ √0.6 ≈ 0.323
total_score = round(50 + 25 × 0.323) = 58
```

- 每個指標的 z 與最終 z 都限制在 ±2，同菜市場找路
- **前測（熟悉場）不進歷史**：10/27 以前前測會被當成之後場次的歷史基準，但前測沒有單輪時限、反應時間跟正式賽不同，不當基準比較合理
- **結算時算好**，存入 `result.z_score` 並回傳；單輪超時自動結束的場次也一樣

## 5. 整理菜籃 market_sort

雷達圖維度：**執行功能（認知彈性）**

程式：`games/market_sort/services.py` 的 `calculate_cognitive_flexibility_score(questions)`

> 玩完一場後，前端一次把 28 題的資料送到後端。**對錯、題目類型（repeat／switch）由前端判斷**。

### 5-1. 4 個指標

程式：`METRIC_RULES = {指標: (權重, 是否越低越好)}`，4 個指標**一律等權重**

| 指標 | 定義 | 方向 | 權重 |
|---|---|---|---|
| 整體正確率 | 28 題答對比例 | 越高越好 | 等權重（各 1/4） |
| switch 正確率 | 規則剛換的題目答對比例（第 1 題不算） | 越高越好 | 等權重 |
| 切換成本 RT | switch 題平均 RT − repeat 題平均 RT（秒，只算答對的題） | 越低越好 | 等權重 |
| 學習速度 | 規則改變後（第 5、10、15 題後），要幾題才追上新規則，3 次取平均 | 越低越好 | 等權重 |

> 10/26 以前每個指標跟寫死的常模比（例如整體正確率 0.80／0.10），數字沒有實際資料依據，已移除；10/27 起權重也改為等權重（原本 0.40／0.25／0.20／0.15 沒有文獻依據）。

> 另外會算「切換成本正確率」和「反應時間變異（rt_cv）」，**只供參考，不參與計分**。

### 5-2. 計算流程

```
① 算出 4 個原始指標
② 每個指標跟「基準」比（基準來自自己過去場次的原始指標 result.raw_metrics，
   資料少時偏向其他使用者，見第 8 節）：
   z = (本場 − 基準平均) ÷ 基準標準差，越低越好的指標反向
③ 每個 z 先限制在 [−2, +2]
④ 等權重合成：合成 = 有資料的指標 z 的平均
⑤ 二階段標準化：加權 z = 合成 ÷ 合成分數的標準差，再限制在 [−2, +2]
⑥ 分數 = round(50 + 25 × 加權 z)          → 1～100
```

- 程式：`games/zscore.py` 的 `composite_z_details`（②～⑤）、`calculate_executive_function_z_score`、`calculate_cognitive_flexibility_score`（整份結果）
- 歷史由 `views.py` 的 `previous_raw_metrics` 用 `session_service` 取出（自己的清單＋其他使用者依使用者分組）後傳入，`services.py` 仍不碰資料庫
- 加權 z 四捨五入到小數 3 位，存入 `result.z_score`（給儀表板用）
- **第一場是熟悉場**：不算分，`z_score`、`cognitive_flexibility_score` 為 `null`，結算 API 的 `current_score`、`encouragement_tier` 也是 `null`，回應多一個 `is_pretest: true`
- **冷啟動**：資料少時偏向其他使用者；全體也不夠 → `z_score`、`cognitive_flexibility_score` 為 `null`；`highest_score`、`recent_scores` 會跳過 `null` 的場次

### 5-3. 資料不足的處理

**單一指標不夠 → 跳過，其他指標照常合成**

- **切換成本 RT**：repeat 題、switch 題都要**各自答對 3 題以上**才計算
- 某個指標的基準不足（例如舊場次沒有這個值）也一樣跳過
- 跳過時，合成分數只用剩下的指標平均；參考場次也只用同一組指標合成，二階段標準化的除數才對得上：

```
切換成本 RT 沒有資料，剩 3 個指標 z = −0.5、−0.667、−0.625
合成 = (−0.5 − 0.667 − 0.625) ÷ 3 = −0.597，再除以合成分數的標準差
```

**整場不夠 → 不給分，回傳 HTTP 400**

| 錯誤代碼 | 情況 |
|---|---|
| `NO_SWITCH_TRIALS` | 整場沒有 switch 題 |
| `NO_REPEAT_TRIALS` | 整場沒有 repeat 題 |
| `INSUFFICIENT_QUESTION_COUNT` | 題數少於 28 題 |

### 5-4. 已拿掉的指標：持續性錯誤率

- 第一版（9/14）權重最高（0.35），9/30 拿掉（commit `9df194a`）
- 原因：籃子會跟著規則一起換，長者選不到「舊規則的籃子」，前端永遠判斷不出持續性錯誤，這一項永遠拿到很好的 z（模擬「28 題只答對 4 題」平均還有 76.6 分）
- 前端最新分支 `fix/pre-meeting-1006`（10/8）這個問題**仍然存在**
- 要加回來需要改玩法（例如固定籃子），待團隊討論

## 6. 冰箱檢查 fridge_check

雷達圖維度：**視覺空間**

### 6-1. 原始總分 `final_score`

程式：`games/fridge_check/services.py` 的 `calculate_final_result`

```
正確率   = 答對題數 ÷ 10 × 100                （重試後答對也算）
速度分   = Σ 每題答對時的速度分                （最高 100）
難度加分 = 中階答對數 × 0.5 + 高階答對數 × 1.0
跳題扣分 = 跳題數 × 2                          （同一題錯 3 次就跳題）

final_score = 正確率 × 0.7 + 速度分 × 0.3 + 難度加分 − 跳題扣分
```

| 答對時的反應時間 | 速度分 |
|---|---|
| ≤ 3 秒 | 10 |
| ≤ 6 秒 | 8 |
| ≤ 10 秒 | 5 |
| > 10 秒 | 3 |

- 只限制 ≥ 0，不設上限：最高 **105.5**（70 + 30 + 中階 3 題 × 0.5 + 高階 4 題 × 1.0）

### 6-2. z-score

**正確率、速度分兩個指標各自跟基準比**（`raw_score` 不再用來算 z）：

```
z_正確率 = (正確率 − 基準平均) ÷ 基準標準差
z_速度分 = (速度分 − 基準平均) ÷ 基準標準差
每個 z 限制在 [−2, +2]
合成     = (z_正確率 + z_速度分) ÷ 2
z        = 合成 ÷ 合成分數的標準差，再限制在 [−2, +2]
standard_score = round(50 + 25 × z)          → 1～100
```

- `raw_score = 正確率 × 0.7 + 速度分 × 0.3`（不含難度加分、跳題扣分）仍然計算並存在結果裡，但**不再用來算 z**：先加權再轉 z 時，波動大的指標會自動佔比較多，寫在公式上的 0.7／0.3 不等於實際影響力；改成各自轉 z 再等權重
- **沒有反應時間資料**（`average_reaction_time_ms` 是 `null`）：速度分只代表「沒資料」，不列入（歷史場次一樣），只剩正確率
- **例**：自己有 3 場歷史 (正確率, 速度分) = (60, 70)、(70, 60)、(80, 80)，兩個指標的基準都是平均 70、標準差 10；兩個指標的 z 是 (−1, 0)、(0, −1)、(+1, +1)，合成 −0.5、−0.5、+1，標準化的除數 √0.6。這場正確率 80、速度分 76 → z_正確率 +1、z_速度分 +0.6 → 合成 0.8 → z = 0.8 ÷ √0.6 ≈ **1.033** → standard_score = round(50 + 25 × 1.033) = **76**
- **第一場是熟悉場**：`z_score`、`standard_score` 為 `null`，建立場次的回應多一個 `is_pretest: true`
- 冷啟動：見第 8 節
- 程式：`calculate_visual_spatial_z_score(accuracy, speed_score, personal_history, population_history)`；歷史由 `session_service.list_previous_results`（自己的）與 `list_previous_results_by_user`（其他使用者，依使用者分組）提供
- 結算 API 回傳 `raw_score`、`z_score`、`standard_score`；歷史 API 的 `score` 是 `final_score`

## 7. 市場買菜 market_shopping

雷達圖維度：**數學**

### 7-1. 原始分數

程式：`games/market_shopping/services.py` 的 `calculate_final_result`

```
total_correct           = 最後有完成的題數（含重試後完成）
first_try_correct_count = 選菜和找零都一次就答對的題數
accuracy                = first_try_correct_count ÷ 10 × 100
速度分                  = Σ 每一步答對時的速度分（選菜、找零各算一次，最高 100）
```

| 答對時的反應時間 | 每一步速度分 |
|---|---|
| ≤ 3 秒 | 5.0 |
| ≤ 6 秒 | 4.0 |
| ≤ 10 秒 | 2.5 |
| > 10 秒 | 1.5 |

> 一題兩步（選菜、找零）滿分 10 分，10 題滿分 100 分；答錯不給速度分。

### 7-2. z-score

做法同冰箱檢查（6-2）：**一次答對率（`accuracy`）、速度分兩個指標各自跟基準比**，等權重合成後做二階段標準化。

```
z_正確率 = (accuracy − 基準平均) ÷ 基準標準差
z_速度分 = (speed_score − 基準平均) ÷ 基準標準差
每個 z 限制在 [−2, +2]
z        = ((z_正確率 + z_速度分) ÷ 2) ÷ 合成分數的標準差，再限制在 [−2, +2]
standard_score = round(50 + 25 × z)          → 1～100
```

- `raw_score = accuracy × 0.7 + 速度分 × 0.3`（沒有反應時間資料時 `raw_score = accuracy`）仍然計算並存在結果裡，但不再用來算 z
- **沒有反應時間資料**（前端沒送 `reaction_time_ms`，`average_reaction_time_ms` 是 `null`）：速度分不列入，只用正確率，單一指標的 z 就是 z
- **例**：歷史同冰箱檢查的 (60, 70)、(70, 60)、(80, 80)；這場一次答對 8 題（正確率 80）、速度分 85 → z_正確率 +1、z_速度分 +1.5 → 合成 1.25 → z = 1.25 ÷ √0.6 ≈ **1.614** → standard_score = round(50 + 25 × 1.614) = **90**
- **第一場是熟悉場**：`z_score`、`standard_score` 為 `null`，建立場次的回應多一個 `is_pretest: true`
- 冷啟動：見第 8 節；程式：`calculate_math_z_score(accuracy, speed_score, personal_history, population_history)`
- 結算 API 回傳 `raw_score`、`z_score`、`standard_score`；歷史 API 的 `score` 是 `raw_score`

### 基準：收縮估計

個人基準不再「滿 3 場硬切換」，改用收縮估計（經驗貝氏，Efron & Morris, 1975）：

```
平均   μ̂  = (n × 自己的平均 + k × 全體平均) ÷ (n + k)
變異數 σ̂² = ((n − 1) × 自己的變異數 + k × 全體的個人內變異數) ÷ ((n − 1) + k)
```

| 符號 | 意思 | 設定 |
|---|---|---|
| n | 這位使用者在這款遊戲（同一階段）的有效歷史場次 | 不含熟悉場、不含這一場 |
| k（`PRIOR_STRENGTH`） | 「先借幾場全體資料」 | 3 |
| 全體平均 | 其他使用者所有有效場次的平均 | – |
| 全體的個人內變異數 | 每位使用者自己場次的變異數，依（場次 − 1）加權合併 | – |

- n = 0 時完全用全體，**熟悉場之後的第一場就能算 z**；n 越大越接近自己的平均與標準差；自己占的比例是 n ÷ (n + k)（API 的 `personal_weight`）
- **為什麼全體用「個人內」變異數**：全體直接算的標準差是「人跟人之間的差異」，通常比「同一個人每次之間的波動」大很多，借來比會把 z 壓扁，等切到自己的歷史時分數才突然大幅擺動
- 每個指標各自套同一個公式，不會出現「正確率跟自己比、反應時間跟全體比」
- k = 3 是保守設定，等長者資料累積後，可用 個人內變異 ÷ 個人間變異 估計

### 二階段標準化

多個 z 加權平均後，波動會變小（指標互不相關時，N 個等權重 z 的平均標準差是 1 ÷ √N），指標多的維度分數就會擠在 50 分附近。所以合成後再除以合成分數本身的標準差：

```
z_最終 = clamp( 合成分數 ÷ σ̂_C , −2, +2 )
σ̂_C² = ((n − 1) × 參考場次合成分數的變異數 + k × 理論變異數) ÷ ((n − 1) + k)
理論變異數 = Σ（正規化後有效權重²）      ← 指標互不相關時的值，不需要資料就能算
```

- 參考場次 = 自己過去的場次，**用這一場同一組基準**算出各場的合成分數（不可以每場用各自當時的基準，尺度會不一致）
- 這一場少了某個指標（例如切換成本 RT 資料不足）時，參考場次也只用同一組指標合成
- 有分階段的遊戲：參考場次依各自最高到達的階段套用跨階段權重，有效權重 = 階段權重 × 階段內指標權重
- 方法依據：複合分數的變異數公式（Nunnally & Bernstein, 1994）；等權重依 Dawes (1979)
- 效果（模擬：每款遊戲隨便發揮、指標互不相關，各 10 萬場）：修正前整理菜籃、聲影日記（4～5 個指標）幾乎拿不到 90 分以上，冰箱檢查（1 個指標）卻有約 6% 的機會；修正後各維度都約 5%，波動一致
- 驗收測試：`games/tests_zscore.py` 的 `SecondStageStandardizationTests`（1 個與 5 個指標各模擬 200 場，最終 z 的標準差差距 < 0.15）

### 熟悉場

- 每位使用者每款遊戲**第一場**（還沒玩完過這款遊戲時開始的場次）是熟悉場：不算分、不進任何歷史（個人、全體都不進）
- 標記在 `GameSession.is_pretest`（沿用既有欄位，不新增欄位）；建立場次時由各遊戲呼叫 `is_first_session` 決定。煮菜過程原本的前測就是熟悉場
- 玩到一半放棄的不算「玩過」，下一場仍是熟悉場；整理菜籃玩完才建立 session，所以第一次送出的那場就是熟悉場
- 聲影日記不設熟悉場（自然說話，沒有操作學習）
- 熟悉場的 `z_score`、`standard_score`（或 `total_score`、`cognitive_flexibility_score`）都是 `null`；建立場次（菜市場找路、市場買菜、冰箱檢查）或結算（整理菜籃）的回應多一個 `is_pretest`，煮菜過程本來就有，前端用它顯示「熟悉場」提示

### 全體資料的範圍

其他使用者的有效場次，且：

- 排除本人（本人的場次是個人歷史，不重複算進全體）
- 排除熟悉場
- 排除 `is_staff` 使用者（測試帳號）
- 排除 demo 帳號的種子資料（遊戲場次 `client_session_id` 以 `seed-` 開頭、日記 `audio_path` 以 `seed/` 開頭）
- 有分階段的遊戲只用同一階段的資料
- 全體的個人內自由度（Σ(場次 − 1)）不滿 3 → 全體基準算不出來，退回只用自己（自己也不滿 3 場就是無資料）

### 冷啟動（每個階段、每個指標分開判斷）

| 情況 | 基準 |
|---|---|
| 自己 0 場，全體個人內自由度 ≥ 3 | 完全用其他使用者（熟悉場之後第一場就有 z） |
| 自己 n 場，全體夠 | 自己占 n ÷ (n + 3)，其他使用者占其餘 |
| 全體個人內自由度 < 3 | 只用自己；自己 ≥ 3 場才算得出，否則這個指標記為無資料 |

### 特殊情況

| 情況 | 處理方式 |
|---|---|
| 歷史每場數值都一樣（標準差 = 0） | 全體的個人內變異數還有值就能算（收縮後變異數 > 0）；全體也是 0 就記為無資料 |
| 某個指標或階段無資料 | 跳過，剩下的權重按比例放大 |
| 全部無資料 | 回傳 `None`，前端顯示「資料不足」，不顯示 0 或假分數 |

### 舊資料重算

新算法上線前結束的場次，`result` 裡的分數是舊算法算的；用指令依新算法重算（只改 `GameSession` 的 `is_pretest` 與 `result` JSON，不改資料表）：

```
python manage.py recompute_scores --dry-run   # 先看會改什麼（在 transaction 裡算完再 rollback，不寫入）
python manage.py recompute_scores             # 正式重算
```

1. 回填熟悉場：每位使用者每款遊戲最早結束的場次 → `is_pretest=True`，其他 → `False`
2. 依序重算每場的 `z_score` 與 1～100 分數（熟悉場為 `null`）
3. demo 帳號的種子場次不動；日記的語言 z 是現算的，不用處理；沒有 `accuracy` 或 `raw_metrics` 的舊結果無法重算，維持原樣
4. 可以重複執行，結果只跟資料有關；程式：`games/management/commands/recompute_scores.py`

- 我們的遊戲跟原測驗在**測驗內容、施測方式、受測族群**上都有不少出入，就算取得常模也不適合直接套用
- 9/16 會議決定：題材、刺激物與計分規則皆自行設計，不使用原測驗的素材或常模

**報告用語建議**

- ❌ 不要說「跟同齡常模比較」
- ✅ 改說「以個人歷史表現為基準的標準分數」
- 各維度採個人參照計分，代表各能力相對使用者自己平常表現的變化，**不是不同能力之間的高低比較**

程式：`dashboard/services.py`（儀表板）、`dashboard/weekly_report.py`（週報表）、`dashboard/diary_zscore.py`（聲影日記語言 z）、`ai_service/weekly_summary.py`（週報一句話總結）

兩支 API 都**只讀資料、不寫入任何資料表**，每次請求當下計算：遊戲從 `GameSession.result.z_score`，聲影日記從 `DiaryAnalysis` 的小分數現算（見 11-4）。

### 11-2. 儀表板 `GET /api/dashboard/`（雷達圖）

```
各維度 z_score = 近 7 天結束場次的 z 平均（四捨五入到小數 3 位，範圍 ±2）
```

- **各維度分開解鎖**（10/27 起）：某維度累計至少 3 筆「有 `z_score`」的場次（篇）就亮起（`unlocked: true`），不用等 6 個都滿。API **永遠回傳 6 個維度**，不再整包回傳 `INSUFFICIENT_DATA`
- **沒解鎖的維度**：`z_score`、`score` 都是 `null`（即使近 7 天有玩也不顯示），`sessions_to_unlock` 是還差幾次，前端畫灰色軸並顯示「再玩 N 次就能看到」
- 解鎖後近 7 天沒玩的遊戲，該軸 `z_score`、`score` 為 `null`，維持解鎖
- **語言軸**：近 7 天有效日記的語言 z 平均，`session_count` 是日記篇數；近 7 天沒有有效日記時為 `null`
- 日記要算得出語言 z 才算進解鎖的 3 篇：更早的日記（自己的、其他使用者的）資料不夠時算不出來。全新系統的第一位使用者要寫 6 篇才會解鎖；若其他使用者已有足夠的日記（個人內自由度 ≥ 3），寫 3 篇就解鎖

回應範例（數值為示意）：

```json
{
  "success": true,
  "data": {
    "period_days": 7,
    "required_sessions": 3,
    "dimensions": [
      { "dimension": "attention", "label": "注意力", "source": "market_route",
        "z_score": 0.375, "score": 59, "session_count": 4,
        "valid_count": 6, "unlocked": true, "sessions_to_unlock": 0, "personal_weight": 0.667 },
      { "dimension": "working_memory", "label": "工作記憶", "source": "memory_recall",
        "z_score": null, "score": null, "session_count": 1,
        "valid_count": 1, "unlocked": false, "sessions_to_unlock": 2, "personal_weight": 0.25 }
    ],
    "encouragement": null
  },
  "error": null
}
```

（`dimensions` 固定 6 筆，範例只列 2 筆）

| 欄位 | 說明 |
|---|---|
| `z_score` | 近 7 天 z 的平均（±2 內，小數 3 位）；沒解鎖或近 7 天沒資料為 `null` |
| `score` | `z_score` 換算的 1～100 分（50 + 25z），`z_score` 是 `null` 時也是 `null` |
| `session_count` | 近 7 天有 z 的場次（篇）數 |
| `valid_count` | 累計有 z 的場次（篇）數，滿 `required_sessions`（3）解鎖 |
| `unlocked` | 是否解鎖 |
| `sessions_to_unlock` | 還差幾次解鎖（已解鎖為 0） |
| `personal_weight` | 個人資料佔基準的比例 n ÷ (n + 3)，n = 這位使用者自己的有效場次（不含熟悉場）；小於 0.5 表示還在「參考期」，基準偏向其他使用者 |

前端顯示規則建議：

| 狀態 | 條件 | 雷達圖該軸 | 文字 |
|---|---|---|---|
| 未解鎖 | `unlocked: false` | 灰色，不畫點 | 「再玩 `sessions_to_unlock` 次就能看到」 |
| 參考期 | 已解鎖且 `personal_weight < 0.5` | 正常顯示 | 「前幾次會參考其他使用者的表現」 |
| 正式 | 已解鎖且 `personal_weight ≥ 0.5` | 正常顯示 | 無 |
| 近 7 天沒玩／資料不足 | 已解鎖但 `score` 為 `null` | 灰色 | 「這週還沒玩」／「資料不足」 |

**機器人卡片 `encouragement`**（程式：`dashboard/encouragement.py`）

**6 個維度都解鎖**時才回傳（否則 `encouragement` 是 `null`）；看的是**總體狀況**，不是只看一週：

```json
"encouragement": { "trend": "up", "overall_score": 71, "previous_overall_score": 66 }
```

```
① 每週分數：同週報（每週各能力 z 平均 → 50 + 25z），那週有分數的能力取平均
② 總體分數：以某一週為基準，基準週和之前所有有資料的週加權平均
   權重 = 0.8 ^ (跟基準週差幾週)，越近的週越重（WEEK_WEIGHT_DECAY）
③ overall_score = 以最近一個有資料的週為基準；previous_overall_score = 以再前一個有資料的週為基準
④ trend：差 ≥ +3 → up、≤ −3 → practice、其他 → steady；只有一週資料 → null
```

- 範例：三週分數 60、70、80 → (60×0.64 + 70×0.8 + 80×1) ÷ 2.44 ≈ 71，前一次 (60×0.8 + 70×1) ÷ 1.8 ≈ 66 → `up`
- 後端只回傳代碼，前端對照文字：`up` 進步了／`steady` 請保持／`practice` 多練習／`null` 歡迎開始
- 趨勢門檻 `TREND_THRESHOLD`、`get_trend`、`overall_score` 放在 `dashboard/services.py`，週報和機器人卡片共用

### 11-3. 週報表 `GET /api/dashboard/weekly-report/`

看「上一個完整的週」（週一～週日），比較對象是再前一週。活動、日記、遊玩時間不設門檻；**能力分數只列已解鎖的維度**。

| 項目 | 算法 |
|---|---|
| 有活動的日子 | 那天有開始玩遊戲或寫日記（沒有登入紀錄表，用這個代替） |
| 能力週分數 | 那週的 z 平均（遊戲依結束時間、日記依建立時間）→ `round(50 + 25 × z)`，限制 1～100 |
| 解鎖 | 到報告週結束為止，該能力累計 3 筆有 z 的場次（篇）→ `unlocked: true`；沒解鎖的能力 `this_week`、`last_week`、`best`、`trend` 都是 `null`（`played` 照常標示這週有沒有碰過）；報告週之後才玩的不會讓舊的報告提前解鎖 |
| 個人最佳 | 到報告週為止，每週分數的最高值 |
| 趨勢 | 本週 − 上週 ≥ +3 → `up`、≤ −3 → `practice`（多練習）、其他 → `steady` |
| 整體表現 | 已解鎖且有分數的能力（含語言）取平均 |
| 一句話總結 | 只把正向事實交給 AI；AI 失敗、超過 40 字或出現禁用詞 → 固定句型 |

> 週報給長者看，**不出現 z 分數等專有名詞、不出現負面字眼**，回傳的都是 1～100 分數和趨勢代碼。

### 11-4. 聲影日記語言 z

程式：`dashboard/diary_zscore.py` 的 `calculate_language_z_score`、`dashboard/services.py` 的 `diary_z_scores`。**不改 `diary/analysis.py`**，只讀它算好、存在 `DiaryAnalysis` 的 5 個小分數。

比照遊戲：每篇日記的每個小分數跟**更早建立的有效日記**比（收縮基準）、每個指標限制 ±2、等權重合成、再做二階段標準化。

```
① 一篇日記的 5 個小分數（每個 0～4 分）
② 每個小分數跟基準比：z = (小分數 − 基準平均) ÷ 基準標準差，限制在 [−2, +2]
   基準 = 自己更早的有效日記＋其他使用者更早的有效日記（收縮估計，見第 8 節）
③ 合成 = 5 個 z 的平均（等權重）
④ 語言 z = 合成 ÷ 合成分數的標準差，限制在 [−2, +2]
⑤ 儀表板：近 7 天各篇語言 z 的平均；週報：每週平均 → 50 + 25z
```

| 指標 | 權重 |
|---|---|
| 流暢度 `fluency_score` | 等權重（各 0.2） |
| 資訊量 `information_score` | 等權重 |
| 句子組織 `sentence_score` | 等權重 |
| 命名 `naming_score` | 等權重 |
| 語意 `semantic_score` | 等權重 |

- **權重**：10/27 起 5 個小分數一律等權重，**不再沿用** `analysis.py` 的 `communication_score` 權重（原本只是沿用雲奇 9/22 訂的權重，來源待確認，也已移除跟它綁定的測試）
- **冷啟動**：基準資料少時偏向其他使用者更早的有效日記（排除本人、`is_staff` 測試帳號、demo 日記）；全體的個人內自由度不滿 3、自己也不滿 3 篇 → 這篇沒有語言 z，不列入平均
- **日記沒有熟悉場**（自然說話，沒有操作學習）
- **只比更早的**：同一時間建立的日記不互相當歷史；7 天以前的日記雖然不算進儀表板平均，仍然會當歷史
- **無效日記**（`is_valid = False`，錄音太短或疑似辨識錯誤）沒有小分數，不算結果也不當歷史
- 一次查出所有有效日記、依建立時間掃過去，不會每篇各查一次資料庫；z 隨時都能現算，**不用存進資料表**
- 範例：自己更早 3 篇的小分數都是 1、2、3（平均 2、標準差 1），這篇小分數都是 3 → 每個指標 z = +1、合成 +1；3 篇歷史的合成分數是 −1、0、+1（變異數和 2），5 個指標等權重的理論變異數 0.2，收縮後 (2 + 3 × 0.2) ÷ (2 + 3) = 0.52 → 語言 z = 1 ÷ √0.52 ≈ **1.387**
- 10/26 以前用寫死的常模（平均 2、標準差 1）；10/27 以前沒有二階段標準化，語言 z 直接是加權平均
